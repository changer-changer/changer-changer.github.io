我们自己做过大约 30 次多智能体实验，超过 20 次栽在协议相关的问题上。端侧小模型尤其惨，就算换到相对听话的模型，也还是有接近一半的实验出协议故障。

那之后我对复杂多智能体拓扑的默认态度变了：先别上。

判断是后来才慢慢钉死的。我们整理过一篇很长的材料，里面真正站住的只有一句：多智能体真正可能赚到的，多半是突破单一 Agent 的系统约束。上下文塞不下、串行跑太慢、贵模型不该干便宜活，这三样各自有用。多挂几个角色，并不会自动变聪明。一旦任务本身不卡那三样，硬拆成一堆角色互相说话，通信、协议和协调都会往里加损耗。

默认架构我现在只留一种：一个主 Agent 持续决策，子 Agent 当成工具按需派生，每轮结果回来再决定下一步。别一上来画一张漂亮的协作拓扑图。

下面是我踩过、也反复在材料里对上的几个坑。

坑一：通信损耗。
模型内部本来在高维表示里跑，跨 Agent 一通信，就得压成一段自然语言或结构化消息，对面再重新理解一遍。细节会丢，语义会偏，多轮还会累计。你传多了，上下文成本涨；传少了，关键事实没了。这不是调个 Prompt 就能消掉的，是跨模型通信本身的代价。

坑二：协议损耗。
协作一复杂，你就得规定 JSON、角色、消息类型、终止条件。模型除了解题，还得守规矩。我们那批实验里，常见翻车是：JSON 写坏、结构化输出不完整、违反通信约定、生成超长被截断。最膈应的是，模型明明能答原题，却卡在协议交互上。解题能力和稳定执行复杂协议的能力，是两回事。

坑三：过早分叉。
任务一开始就一次性规划好谁负责什么、怎么互传，听起来很厉害。实际上那时你还不知道哪条路会死、哪条会冒出新信息。我们观察到，一次性规划拓扑，往往不如根据实时结果逐轮派活。每一轮决策能用上上一轮刚拿到的信息，不确定性才会掉下来。黑客松里我也栽过类似的：第一版就想同时上多 Agent、长期记忆、自动检索和完整工作台，结果基础功能都没稳。后来改成先做一个最小能演示的版本，再往上加。

坑四：上下文卸载用错时机。
多智能体有个真收益叫上下文卸载：主 Agent 把十个相对独立的方向扔给十个子 Agent，各自探索，只回收关键结果和证据。这在资料海量、分支互相干扰时有用。但如果任务本身上下文不大、也不需要并行探索，你还硬拆，只是在给自己制造通信和协议成本。先问一句：单一 Agent 是不是已经卡在窗口、吞吐或成本上了？没卡，就别拆。

坑五：把 Debate 当成“智力涌现”。
多候选、评审、辩论有时确实能抬成功率。可很多时候抬的是采样和验证：多抽几次，再找个能辨对错的验证器挑出来。生成正确答案难、识别正确答案相对容易时，这招才划算。验证器自己也分不清对错，多挂几个评审 Agent 没用。别把 Best-of-N 和验证，直接讲成“多智能体变聪明了”。

如果你要动手，我建议直接抄这份清单：

1. 默认单主 Agent。能自己干完就别派生。
2. 子 Agent 当工具：任务写清楚，返回结果加证据，主 Agent 验收后再决定下一步。
3. 只有三种情况认真考虑拆：上下文真装不下或互相污染、需要并行探索缩短墙钟时间、简单活可以路由给更便宜的模型。
4. 协议尽量薄。能少一种消息类型就少一种。小模型更别堆复杂 JSON 仪式。
5. 别在任务开头锁死拓扑。跑一轮、看结果、再派下一轮。
6. 要评审就先确认：验证比生成更容易。测不过的验证器，加了也白加。
7. 评复杂方案时，拿“主 Agent + 按需子 Agent”当基线。它赢不了简单架构，就别为了拓扑好看上线。

复杂拓扑不是不能研究。但要证明的是：同样模型、相近算力、同一任务下，它是否比按需派生子 Agent 更有效。证不出来，多角色、多通信边、更重的协议，就只是在加成本和失败面。

你现在手头那个多智能体项目，拆开之后，卡的是上下文、速度、成本，还是其实只是想多挂几个角色？评论区扔一句，我按这套清单帮你看该不该拆。
