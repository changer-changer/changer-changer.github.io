根目录一度堆了十几篇日记和一堆散件，同内容还在别的文件夹里各有一份。我后来做了一次 md5 核对，确认是同步把旧副本又带回来了，才整批挪进回收站。从那以后我才认真把知识库当成给人和给 Agent 共用的记忆来管。

我现在的库大概分几层。

最上面是导航页。就一个文件，写清楚：想找什么，进哪个入口。生活操作系统、原则与认知、日记、项目、常用积累、个人档案，各有固定位置。新来的 Agent 先读这一页，少问十句“东西在哪”。

生活这块我单独做成了「操作系统」。每个域一个子文件夹，顶部永远只有一份「当前状态」：自动运行中的事，和接下来要自动化的事。讨论过程扔进「历史/」，按日期加主题命名。当前状态永远最新、永远短，历史负责留过程。原则、隐私事实、日记原料不塞进这里，分别放到原则库、个人档案、日记目录，避免同一件事存三份还对不上。

原则与认知按问题拆，不按“内容像什么”拆：世界怎么运作、人类是什么、我要什么、怎么达到、在哪些场景用。打开文件夹的顺序，就是在复述一遍自己的认知框架。日记当矿藏只读，定期蒸馏进框架，不拿日记原文当最终结论。

日常流入靠 Inbox。新东西先扔进去，确认用途后再归档到对应编号目录。我吃过亏：根目录图省事直接落文件，过两周就散乱，再遇到多端同步，冲突副本会把已归位的东西又吐回根上。现在的规矩是根目录尽量空，日记进日记目录，散件进 Inbox 或直接进归属文件夹。

给 Agent 当记忆时，我只暴露会同步的笔记文件夹，放待办、长期目标、常用资料和操作系统当前状态。权限宁可少给。密码、私聊原文、别人的信息，不往它能随便读的位置塞。Agent 改完笔记，等于改了它脑子里的世界，所以同步冲突比“笔记找不到”更危险：两台设备各改一版，很容易冒出同名副本，人眼一时看不出来。

改名这件事我也交过学费。一次只在同一父目录里改文件夹名，改完立刻修导航表和活文档里的链接，旧路径写进回退说明。跨共享边界乱挪，或者只改名不修链，后面 Agent 和人都会踩空。导航页存在的意义，就是让改名成本可控：先改入口，再改实体。

别人要照抄，我不建议一上来复制我的全套编号。最小能跑的结构可以只有这些：

1. 一个 Inbox。所有新东西先到这。
2. 一个导航页。十行以内，写清入口。
3. 两到三个常用桶。比如「进行中的项目」「可复用的原则或方法」「原始日记或讨论」。
4. 每个重要主题一份「当前状态」，讨论过程另存历史，别把过程写进状态文件里无限变长。
5. 网盘多端同步开着，但根目录保持干净；发现冲突副本，先比对再删，别凭感觉覆盖。
6. 如果要给 Agent 读，单独划一块同步目录当记忆，并写明它能改什么、不能碰什么。

我后来还加了维护协议：个人事务对话先读当前状态，相关内容当场落盘；知识库和操作系统各有定时蒸馏，避免全靠人记得整理。你不一定要上自动化。先把 Inbox、导航、当前状态这三件稳住，已经比大多数堆了一堆 Markdown 却找不到入口的库好用。
